- **2026-11-11 — §7 exploratory parenthetical corrected against the committed artifact.** The registration text says the coefficient intervals show "in-sample AUC 0.645; no coefficient interval excludes zero". That contradicts the committed `paper/reports/v7/g1_values.json`, whose `coef_ci` gives `c0_pos_corr` a 95% task-cluster bootstrap interval of [0.0213, 0.8949] — one interval excludes zero; the other six do not. Affected analyses: none confirmatory (§7's intervals are exploratory); the correction matters for the paper's `N1_TOP_PREDICTORS` phrasing, which must name `c0_pos_corr` as the one feature whose interval excludes zero. Result both ways: identical — this is a wording correction only. Also in this change: three comment-only clarifications with no behavioral effect (`v7_g1_freeze.py` `seed_out` definition vs guide G1.5; `builder.candidate_prs` created-date vs merge-date ordering; `fliprisk.fit` unpenalized-intercept singularity note), found in the whole-branch review.

- **2026-11-11 — implementation fixes and G4 set-up, before any G4 data were collected.** Three defects in the `gtb6` patch and test tools surfaced on the first real tasks and are fixed, each pinned by a test that failed first (`paper/tests/test_gtb6_repo_ops.py`): (1) `repo_ops.apply_patch` now normalizes the competition patches, which have no final newline (all 230 `patch`/`test_patch` fields of the 115 tasks) and write whole-file creations and deletions with `a/`/`b/` headers instead of `/dev/null` (101 creations); without it no reference test patch applied. (2) `gtb6.outcomes` writes node ids relative to the invocation directory, not pytest's rootdir (rich keeps a `pytest.ini` in `tests/`), so the ids can be run again. (3) Tests are selected by node id through `gtb6.outcomes` (`--gtb-select` file) and only test files go on the command line, because requests' parametrized ids contain `::` (IPv6 URLs), which the pytest versions of the dated environments cannot parse as targets. Set-up choices of the G4 driver (`paper/scripts/v7_g4_trace.py`), not fixed by the registration: the base tree is the competition snapshot's checked-out HEAD (the snapshots' git history is a re-export and does not contain the `base_commit` objects; the registered candidates come from the same snapshot); dependencies are the guide's G4.2 install lines, resolved as of each task's `created_at` (`uv pip install --exclude-newer`), inside Docker; traced definitions are mapped to graph IDs through the candidate binding (§4 "same alias rules": an exact ID, else the unique candidate bound to the same definition span). Affected analyses: H7 and the §5.2 traced-error numbers, and Plan 3's patch evaluation (same `repo_ops`). Result both ways: not applicable — without the fixes no task could be evaluated.

- **2026-11-11 — post-cutoff selection: the closing-reference pattern now matches the registered text, before any task was built.** §2.2 says a pull request qualifies if "its body says it closes, fixes or resolves an issue". The committed `gtb6.builder.CLOSES` accepted only the `KEYWORD #N` form, which is narrower than that text and than GitHub's own closing references. Phase A of the G5 build (2026-11-11) found 20 qualifying pull requests across the three repositories (18 with a real issue, 8 with the issue opened after the cutoff), below the registered minimum of 40 even under the fallback; a check of every merged pull request since the cutoff in psf/requests and Textualize/rich found 19 more whose bodies close an issue in the URL form (`Fixes https://github.com/Textualize/rich/issues/3762`), which rich uses throughout. `builder.closed_issue` now accepts GitHub's forms — `KEYWORD[:] #N`, `KEYWORD OWNER/REPO#N` and `KEYWORD https://github.com/OWNER/REPO/issues/N` — counting only issues of the same repository, the first one in the body as registered (`paper/tests/test_gtb6_builder.py`). Phase A was rerun from scratch. Affected analyses: the composition of the post-cutoff set (H4/H8 out of sample). Result both ways: the narrower pattern's pool counts are kept above and in `paper/results/2026-11-11_g5_build/details_cache_hash_only_pattern.json` (with its fetch log); no task had been built, and no model output exists for either pool.

- **2026-11-11 — post-cutoff graphs: PyCG 0.0.7 with a two-line patch, capped at two iterations, fixed hash seed; decided by the participant before any graph was built.** §2.3 registers "PyCG (pinned version recorded in the lock file) over all package modules". Measured on the three repositories' current heads (`paper/pycg/STUDY.md`): the PyPI wheel of pycg 0.0.8 cannot run on a case-sensitive filesystem; pycg 0.0.7 crashes on requests (positional-only defaults, PEP 570) and never reaches its fixed point on rich (no finish in 30 min; 4–8 iterations do not finish in 25 min; 3 iterations explode to 131,025 edges); and its output depends on Python's hash seed. Strictly as registered, rich and requests would be excluded as "PyCG failed", leaving about 4–6 fastapi tasks. The participant chose (2026-11-11) to keep PyCG with: pycg 0.0.7 + `setuptools==75.8.0`, the patch `paper/pycg/pycg-0.0.7-posonly-defaults.patch`, `--max-iter 2` for every repository, and `PYTHONHASHSEED=0` (`builder.run_pycg`, `v7_g5_build.py`). Affected analyses: the post-cutoff graphs (H4/H8 out of sample, H8 features). Result both ways: the registered rule's outcome is reported as the count of candidates PyCG fails on without the cap and patch (rich and requests: all). Capped graphs are less complete than a fixed point (fastapi 1,627 vs 2,146 edges); this is reported as a limitation. Even so, the post-cutoff pool holds 38 candidates with a real issue (26 with the issue opened after the cutoff), below the registered minimum of 40, so the fallback rule applies and N is reported as built.
